# Client operations

Every field on the client is an intent-builder sub-client: an entry captures what to do (`client.deposit.of(...)`), a route pin narrows how (`.selfFunded()`), and a terminal does it (`.send()`, `.approve()`, `.action()`).

Settlement is **cycle-based**. Core nets each participant's obligations for a clearing cycle into a single net-debit or net-credit committed to an on-chain Merkle root. Participants settle by fetching their prepared clearing action (contract address, amount, and Merkle proof) from core, then calling the `ClearingHouse`. `cycleId` is core's text cycle id (`cycle_id_text` in clearing proofs and actions, `"{asset}:{period_start}"`); core does not resolve the on-chain `bytes32` id in this path.

## Deposits and withdrawals

Deposit collateral, then sign a payment:

```ts
// Deposit ETH collateral (in wei); null asset = native ETH
await client.deposit.of(null, 1_000_000_000_000_000n).send(); // 0.001 ETH

// Build a payment for the asset's active settlement cycle, then sign it
const payload = await client.payment.newPayment(
  recipientAddress,
  "1000", // amount in the asset's base units
); // asset omitted = native ETH

const request = await client.payment.signRequest(payload);
```

To deposit an ERC20 token, grant the allowance first:

```ts
await client.deposit.of(tokenAddress, "1000").selfFunded().approve();
await client.deposit.of(tokenAddress, "1000").send();
```

<Note>
  `approve()` returns `undefined` when the existing allowance is already
  sufficient. A deposit with a missing allowance is refused with a typed
  `Erc20AllowanceRequiredError` before any gas is spent.
</Note>

Withdrawals are timelocked, one builder per step:

```ts
await client.withdraw.request(tokenAddress, "500").send(); // grace period starts
await client.withdraw.cancel(tokenAddress).send(); // before the timelock expires
await client.withdraw.finalize(tokenAddress).send(); // after it elapses
```

## Payment guarantees

The payer signs a payment; the recipient redeems it for the operator's receipt and verifies it:

```ts
// Payer side
const payload = await client.payment.newPayment(recipientAddress, amount, asset);
const request = await client.payment.signRequest(payload);

// Recipient side
const receipt = await client.payment.issueGuarantee(request);

// Verify: check the operator's ECDSA signature offline and decode the guarantee
const guarantee = await client.payment.verifyGuarantee(receipt);
// guarantee.client, guarantee.recipient, guarantee.amount, guarantee.asset, …
```

### `client.payment` methods

- `newPayment(recipient, amount, asset?)` — a payment payload scoped to the asset's active settlement cycle.
- `signRequest(payload)` — sign the payload as the payer, returning a `PaymentRequest`.
- `issueGuarantee(request)` — redeem a signed request for the operator's `GuaranteeReceipt`.
- `verifyGuarantee(receipt)` — check the receipt was signed by the operator signer core publishes, and return the `Guarantee` it attests.
- `listReceived()` — payments guaranteed to the signer as a recipient.
- `checkpointActiveCycle(asset?)` / `checkpointCycle(asset, cycleId)` — sign and submit a checkpoint (see [Checkpoints](#checkpoints)).

<Note>
  Verification is offline. A service that never builds a `Client` can run the
  same check with `verifyGuaranteeReceipt(receipt,
  guaranteeRegistryDomain(chainId, guaranteeRegistryAddress), guaranteeSigner)`,
  taking the three values from core's public parameters.
</Note>

## Settling a cleared cycle

The debtor pays what they owe; the creditor claims what they are owed. Terms always come from core's prepared action — the caller only names which cycle.

```ts
// Debtor: pay the committed net debit
await client.settlement.pay(cycleId).send();

// ERC-20 cycles need the ClearingHouse allowance first
await client.settlement.pay(cycleId).selfFunded().approve();

// Creditor: claim the committed net credit
await client.settlement.claim(cycleId).send();

// Sponsor someone else's claim (the payout still goes to the committed leaf)
await client.settlement.claim(cycleId).creditor(creditorAddress).send();

// Inspect the prepared terms without sending anything
const action = await client.settlement.pay(cycleId).action();
```

## Gasless routes

With a `facilitatorUrl` configured, deposits, withdrawals, and settlement can run without the
signer paying gas: the signer produces an EIP-712 authorization and the facilitator submits it at
its own expense. Every route credits the authorization's signer — the choice only changes who
pays — and the receipt's `route` field reports which one ran.

```ts
// Auto route: EIP-3009, then Permit2 with the approval sponsored, then self-funded.
await client.deposit.of(usdc, 1_000_000n).send();

// Pin a scheme; a pinned route fails rather than trying another one.
await client.deposit.of(usdc, 1_000_000n).gasless().send();
await client.deposit.of(usdc, 1_000_000n).permit2().sponsorApproval().send();

// Sign now, submit elsewhere — the submitter needs no signer of their own.
const auth = await client.deposit.of(usdc, 1_000_000n).eip3009().sign();
await client.deposit.of(usdc, 1_000_000n).eip3009().authorization(auth).verify();
await client.deposit.of(usdc, 1_000_000n).eip3009().authorization(auth).send();

// Withdrawals work for ETH too; settlement debits pin the nonce to the cycle id.
await client.withdraw.request(null, amount).gasless().send();
await client.settlement.pay(cycleId).gasless().send();
```

<Note>
  Native ETH has no gasless deposit route — no authorization scheme covers it —
  and native-asset debits cannot be pulled by signature. Both self-fund.
  `client.deposit.isGaslessAvailable()` reports whether a facilitator is
  configured at all. A rejection surfaces as `FacilitatorRejectedError`
  carrying the facilitator's snake_case reason (such as `rate_limited`) as
  `code`; an `OutcomeUnknownError` means the facilitator
  may already have submitted — do not blindly retry it.
</Note>

## Balances

```ts
const positions = await client.account.assets(); // per-asset on-chain positions
const balance = await client.account.assetBalance(tokenAddress); // core's view, incl. locked
const tokens = await client.tokens.supported(); // depositable assets
```

`client.account.stablecoinPosition(token)` reports a stablecoin pool position: the principal and yield split, plus the pool's share accounting — `userShares`, `totalUserShares`, `protocolShares`, `poolShares`, `poolAssets`, and the `strategy` backing the pool (the zero address while its assets sit idle).

## Building payments

Build payments with `client.payment.newPayment`. A payment is scoped to the asset's active settlement cycle, which it reads from core, so it cannot be built offline. It is stamped by core's clock rather than this machine's, gets a random `uint256` `reqId`, and a random `salt` that blinds the recipient. The asset defaults to the zero address, which represents native ETH.

```ts
const payload = await client.payment.newPayment(
  recipientAddress,
  amount, // number | bigint | string
  erc20Token, // optional; omit for native ETH
);
// payload.cycleId, payload.reqId, payload.timestamp, payload.salt, …
```

`signRequest` signs it as an EIP-712 `PaymentAuthorization` under the ClearingHouse domain, through the signer's `signTypedData`:

```ts
const request = await client.payment.signRequest(payload);
// request.payload, request.signature
```

## Validated guarantees

A payer can agree that a guarantee only becomes payable once an external validator approves it, by attaching a `ValidationRequirement` to the payload before signing. The requirement is bound into the salted recipient commitment the payer signs:

```ts
import { ValidationRequirement } from "@4mica/sdk";

const payload = (
  await client.payment.newPayment(recipientAddress, amount, erc20Token)
).withValidation(
  new ValidationRequirement({
    validator: "validator-id", // must be on core's allowlist
    subject: "0x…32-byte hash…", // what the validator must approve
    deadline: 1700000600, // optional; core tightens it to the cycle cutoff
    params: "0x…", // optional validator-specific policy bytes
  }),
);

const request = await client.payment.signRequest(payload);
const receipt = await client.payment.issueGuarantee(request);
```

In the x402 flow, the same requirement travels as `extra.validation` on the payment requirements and is attached automatically.

## Checkpoints

A checkpoint is the payer's signed running total of its payments in a cycle. Core caps how many guarantees a payer may hold past its latest checkpoint; past the cap, issuance is refused with a `CheckpointRequiredError`. Only the payer can sign its checkpoint, so run these on the payer's client.

```ts
import { CheckpointRequiredError } from "@4mica/sdk";

// Cover everything outstanding in the asset's active cycle
await client.payment.checkpointActiveCycle(erc20Token); // undefined when there is nothing to cover

// Or cover the cycle a refusal names, then retry
try {
  await client.payment.issueGuarantee(request);
} catch (err) {
  if (err instanceof CheckpointRequiredError) {
    await client.payment.checkpointCycle(
      err.details.assetAddress,
      err.details.cycleId,
    );
  }
}
```

Both methods retry once when core answers `CheckpointMismatchError` because the batch moved while it was being signed. `cycleId` here is the on-chain `bytes32` id, not the text id settlement takes.

<Note>
  Core's batch is checked before it is signed: every payment must be one the
  payer signed, in this cycle and asset, past the previous checkpoint, and
  counted once. A batch that fails those checks throws
  `UntrustedCheckpointBatchError` rather than being signed, since signing it
  could inflate what the payer can be charged on default.
</Note>

## Transaction receipt options

On-chain terminals accept an optional final `waitOptions` argument to override receipt polling: `{ timeout?, pollingInterval?, gas? }`.

```ts
await client.deposit.of(tokenAddress, "1000").send({
  timeout: 90_000,
  pollingInterval: 2_000,
});
```
