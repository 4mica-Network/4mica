# Client operations

Every field on the client is an intent-builder sub-client: an entry captures what to do (`client.deposit.of(...)`), a route pin narrows how (`.selfFunded()`), and a terminal does it (`.send()`, `.approve()`, `.action()`).

Settlement is **cycle-based**. Core nets each participant's obligations for a clearing cycle into a single net-debit or net-credit committed to an on-chain Merkle root. Participants settle by fetching their prepared clearing action (contract address, amount, and Merkle proof) from core, then calling the `ClearingHouse`. `cycleId` is the on-chain `bytes32` cycle identifier (the text form works too).

## Deposits and withdrawals

Deposit collateral, then sign a payment guarantee request:

```ts
import { PaymentGuaranteeRequestClaims } from "@4mica/sdk";

// Deposit ETH collateral (in wei); null asset = native ETH
await client.deposit.of(null, 1_000_000_000_000_000n).send(); // 0.001 ETH

// Build and sign a payment guarantee request
const claims = PaymentGuaranteeRequestClaims.new(
  userAddress, // payer address
  recipientAddress,
  reqId, // random uint256 nonce — uniqueness is all core asks of it
  "1000", // amount in the asset's base units
  Math.floor(Date.now() / 1000), // timestamp (seconds)
);

const { signature, scheme } = await client.payment.signRequest(claims);
```

To deposit an ERC20 token, grant the allowance first:

```ts
await client.deposit.of(tokenAddress, "1000").selfFunded().approve();
await client.deposit.of(tokenAddress, "1000").send();
```

<Note>
  `approve()` returns `undefined` when the existing allowance is already
  sufficient. A deposit with a missing allowance is refused with a typed
  `Erc20AllowanceRequiredError` before any gas is spent.
</Note>

Withdrawals are timelocked, one builder per step:

```ts
await client.withdraw.request(tokenAddress, "500").send(); // grace period starts
await client.withdraw.cancel(tokenAddress).send(); // before the timelock expires
await client.withdraw.finalize(tokenAddress).send(); // after it elapses
```

## Payment guarantees

The payer signs a request; the recipient redeems it for a BLS certificate and verifies it:

```ts
// Payer side
const { signature } = await client.payment.signRequest(claims);

// Recipient side (the signer must be the claims' recipient)
const cert = await client.payment.issueGuarantee(claims, signature);

// Verify: BLS-check against the operator key, decode, and match the domain
const verified = await client.payment.verifyGuarantee(cert);
```

### `client.payment` methods

- `signRequest(claims, scheme?)` — sign a payment guarantee request as the payer.
- `issueGuarantee(claims, signature)` — redeem a payer's signature for a BLS-signed certificate.
- `verifyGuarantee(cert)` — BLS-verify a certificate, decode it, and validate its domain separator.
- `listReceived()` — payments guaranteed to the signer as a recipient.
- `guaranteeDomain` / `guaranteeDomains` — the domain separator(s) certificates are issued under.

<Note>
  Certificate verification requires the optional `@noble/curves` dependency for
  BLS decoding.
</Note>

## Settling a cleared cycle

The debtor pays what they owe; the creditor claims what they are owed. Terms always come from core's prepared action — the caller only names which cycle.

```ts
// Debtor: pay the committed net debit
await client.settlement.pay(cycleId).send();

// ERC-20 cycles need the ClearingHouse allowance first
await client.settlement.pay(cycleId).selfFunded().approve();

// Creditor: claim the committed net credit
await client.settlement.claim(cycleId).send();

// Sponsor someone else's claim (the payout still goes to the committed leaf)
await client.settlement.claim(cycleId).creditor(creditorAddress).send();

// Inspect the prepared terms without sending anything
const action = await client.settlement.pay(cycleId).action();
```

## Building claims

Build claims with the `PaymentGuaranteeRequestClaims.new` factory. It normalizes addresses and parses `uint256` values. The asset defaults to the zero address, which represents native ETH.

```ts
import { PaymentGuaranteeRequestClaims, SigningScheme } from "@4mica/sdk";

const claims = PaymentGuaranteeRequestClaims.new(
  userAddress,
  recipientAddress,
  reqId, // number | bigint | string — a random uint256 nonce
  amount, // number | bigint | string
  timestamp, // seconds
  erc20Token, // optional; omit for native ETH
);
```

Signing uses `SigningScheme.EIP712` by default. Use `SigningScheme.EIP191` for wallets that do not support typed data:

```ts
const { signature, scheme } = await client.payment.signRequest(
  claims,
  SigningScheme.EIP191,
);
```

## Validated guarantees

A payer can agree that a guarantee only becomes payable once an external validator approves it, by attaching a `ValidationRequirement`:

```ts
import {
  PaymentGuaranteeRequestClaims,
  ValidationRequirement,
} from "@4mica/sdk";

const claims = PaymentGuaranteeRequestClaims.new(
  userAddress,
  recipientAddress,
  reqId,
  amount,
  timestamp,
  erc20Token,
).withValidation(
  new ValidationRequirement({
    validator: "validator-id", // must be on core's allowlist
    subject: "0x…32-byte hash…", // what the validator must approve
    deadline: 1700000600, // optional; core tightens it to the cycle cutoff
    params: "0x…", // optional validator-specific policy bytes
  }),
);

const { signature } = await client.payment.signRequest(claims);
const cert = await client.payment.issueGuarantee(claims, signature);
```

In the x402 flow, the same requirement travels as `extra.validation` on the payment requirements and is attached automatically.

## Transaction receipt options

On-chain terminals accept an optional final `waitOptions` argument to override receipt polling: `{ timeout?, pollingInterval?, gas? }`.

```ts
await client.deposit.of(tokenAddress, "1000").send({
  timeout: 90_000,
  pollingInterval: 2_000,
});
```
