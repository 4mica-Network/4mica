---
title: "Make Paid Requests Automatically"
description: "Use client wrappers to turn HTTP 402 responses into automatic paid retries."
---

The best experience is simple for the agent and controlled for the operator. Your code calls a protected resource normally, `client.fetch` handles the paid retry, and spend limits decide whether the payment is signed.

Automatic payment does not mean unlimited payment. Treat `client.fetch` as the transport layer and your limits and policy as the guardrail.

## What `client.fetch` handles

`client.fetch` has the same signature as the global `fetch` and handles the payment mechanics around a normal HTTP request.

<Steps>
  <Step title="Read payment requirements">
    On an HTTP 402, it reads the seller's 4Mica payment options from the response.
  </Step>
  <Step title="Check spend limits">
    It picks the first option the session's spend limits allow. If none passes, it throws `SpendLimitError` and signs nothing.
  </Step>
  <Step title="Sign the guarantee">
    It signs a payment guarantee with a fresh request ID, using the session's wallet.
  </Step>
  <Step title="Retry the request">
    It sends the request again with the payment header attached. It retries once; a second 402 comes back to you as is.
  </Step>
  <Step title="Return the response">
    Your agent receives the paid response like a normal HTTP result.
  </Step>
</Steps>

Any response other than a 402 is returned untouched, and so is a 402 that offers no 4Mica payment on a network the session has open. The session's network is always open; another network opens once you use it through the `{ network }` option of another call, such as `client.balance({ network })`.

## Pay with `client.fetch`

```ts
import { FourMica, SpendLimitError } from "@4mica/sdk";

await using client = await FourMica.connect({
  privateKey: process.env.PRIVATE_KEY,
  network: "base-sepolia",
  spend: {
    perPayment: "0.25 USDC",
    total: "10 USDC",
    payTo: ["0xSellerAddress"],
  },
});

try {
  const response = await client.fetch("https://api.example.com/research");
  console.log(client.paymentFor(response)); // what was paid, or undefined
} catch (err) {
  if (!(err instanceof SpendLimitError)) throw err;
  console.warn(`refused by ${err.limit} for ${err.url}`); // nothing was signed
}
```

After the first paid retry succeeds, check the corresponding wallet activity in [4mica dashboard](https://app.4mica.io).

## Spend limits

Set limits once, in `FourMica.connect({ spend })`. Amounts are written like deposits, as a decimal string with the asset.

| Option | Default | Meaning |
| --- | --- | --- |
| `perPayment` | `"1 USDC"` | Most one payment may cost, per asset. A string, or an array for several assets: `["1 USDC", "0.0005 ETH"]`. |
| `total` | No limit | Most the whole session may pay, per asset. Same format as `perPayment`. |
| `payTo` | Any address | Only pay these seller addresses. |

- **A payment is only allowed in an asset that has a `perPayment` entry.** A seller cannot get round the cap by asking for a different token. With the default, the session pays only USDC.
- **`total` counts every payment the session sends**, reserved before signing so concurrent requests cannot overshoot it. A payment that was never sent because signing threw, or that the seller refused with a 402, is released again. One that was sent stays counted even if the request then fails or the seller answers with an error, because the seller may still redeem it.
- **`total` is local to one session.** The count is kept in memory by the process that called `connect`: a new `connect` starts from zero, and several processes sharing a wallet each get their own `total`. Across all of them, the hard limit is the collateral the wallet has deposited.
- **Violations throw `SpendLimitError`** before anything is signed. `err.limit` names the limit (`"perPayment"`, `"total"`, `"assets"` or `"payTo"`) and `err.url` the resource.
- **A limit in an asset the network does not list does not apply there**, so one `spend` setting can cover several networks.

## Organization spending policies

Spend limits live in one process. To check payments against the spending policies your organization sets in the [4mica dashboard](https://app.4mica.io) (per-payment, daily and monthly limits, allowed recipients, frozen keys, and approvals above a threshold), pass `governance` with an API key that has the `SPEND_AUTHORIZE` scope:

```ts
import { FourMica, SpendAuthorizationError } from "@4mica/sdk";

await using client = await FourMica.connect({
  privateKey: process.env.PRIVATE_KEY,
  spend: { perPayment: "5 USDC" },
  governance: {
    apiKey: process.env.FOURMICA_API_KEY!,
    approvalTimeoutMs: 10 * 60_000,
  },
});

try {
  await client.fetch("https://api.example.com/report");
} catch (err) {
  if (!(err instanceof SpendAuthorizationError)) throw err;
  console.log(err.reason, err.deniedReason, err.approvalRequestId);
}
```

Before signing, `client.fetch` asks `POST /v1/spend/authorize` for the payment's network, asset, amount, payer and recipient, after the session's own `spend` limits have passed:

- **Reserved**: the payment is signed and sent, and from then on only a definitive rejection gives the reservation back. The authorization is released, and the amount freed from `total`, only when signing throws (nothing was sent) or the seller answers the payment with a fresh 402. Every other outcome consumes the authorization with the payment's `reqId`: a successful response, but also a seller error (any other non-2xx), a timeout, a network failure or an aborted request, because the seller holds a signed payment it may still redeem. Counting it is the safe side, and 4mica reconciles by `reqId` once the seller reports the payment.
- **Denied**: nothing is signed, and `client.fetch` throws `SpendAuthorizationError` with `reason: "denied"` and `deniedReason` (`"frozen"`, `"recipient_not_allowed"`, `"per_payment_limit"`, `"daily_limit"`, `"monthly_limit"`, `"approval_rejected"`, `"approval_expired"` or `"limit_changed"`).
- **Pending approval**: the amount is above a policy's approval threshold. `client.fetch` polls every `pollIntervalMs` (default 2 s) until someone in your organization decides, for up to `approvalTimeoutMs` (default 5 minutes). If time runs out the authorization is released and it throws `SpendAuthorizationError` with `reason: "approval_timeout"` and the `approvalRequestId` to follow up on.
- **The API refuses the request** (for example the payer wallet is not one of your organization's, or the key is for another environment): nothing is signed and the `AppError` is thrown.

`agentId` attributes payments to one agent when the key is not already an agent's key.

### Cancellation and deadlines

Every call to the 4mica API is bounded by `requestTimeoutMs` (default 10 s), and the whole decision, from the first `authorize` request through every approval poll, by `approvalTimeoutMs`, which starts before the first request. The request's `signal` is honoured differently on each side of submission:

- **Before the payment is sent** (authorizing, waiting between polls, a poll request, signing): aborting the `signal` stops at once and `client.fetch` rejects with the signal's reason. A pending approval or a reservation that was already granted is released first, and that release is bounded by `accountingTimeoutMs`. If the abort lands while the first `authorize` request is in flight, its response is never read, so a reservation the API may have made is not released; it stops counting when it expires.
- **After the payment is sent**: the seller may redeem it, so the consume (or the release after a 402) runs to completion under its own lifecycle, `accountingTimeoutMs` (default 30 s) for all attempts together, and ignores the request's `signal`. Aborting the request still rejects `client.fetch` as soon as the paid request does.

### Accounting after the payment

Consuming or releasing the authorization is bookkeeping that happens after the seller has answered, so its failure never turns a payment into an error: `client.fetch` still returns the seller's response, unchanged. A network error, a 5xx or a 429 from the 4mica API is retried up to three attempts in all, with jittered backoff; any other 4xx is not retried. Both calls are idempotent, so a retry never counts a payment twice.

`governanceOutcome(response)` tells you how the bookkeeping went for a response that carried a governed payment, and returns `undefined` otherwise:

- `accounting: "recorded"`: the authorization was consumed, or released after a 402.
- `accounting: "pending"`: the call did not finish within `accountingTimeoutMs`, so the outcome is not known yet. A consume is reconciled by `reqId` once the seller reports the payment; a release lapses when the reservation expires.
- `accounting: "failed"`: the API refused the call, or every attempt failed.

To alert on it, pass `onAccountingError`. It receives a `SpendAccountingError` with the `transition` (`"consume"` or `"release"`), `authorizationId`, `reqId`, `accounting` and the underlying `cause`, for every outcome other than `"recorded"`, including when the paid request itself threw:

```ts
import { FourMica, governanceOutcome } from "@4mica/sdk";

await using client = await FourMica.connect({
  privateKey: process.env.PRIVATE_KEY,
  governance: {
    apiKey: process.env.FOURMICA_API_KEY!,
    onAccountingError: (err) => console.warn(err.authorizationId, err.message),
  },
});

const res = await client.fetch("https://api.example.com/report");
console.log(governanceOutcome(res)); // { authorizationId: "…", accounting: "recorded" }
```

Do not pay again because accounting failed: the payment went through, and the spend is reconciled from the seller's report.

The Python SDK (`sdk-4mica`) has the same behavior: pass `governance=GovernanceOptions(api_key=..., agent_id=..., approval_timeout_secs=..., poll_interval_secs=..., on_accounting_error=...)` to `FourMica.connect`, catch `SpendAuthorizationError`, and read `client.governance_for(response)`. A task cancelled while a consume or release is being retried plays the part of an aborted `signal`: `on_accounting_error` receives `accounting="pending"`, then the cancellation propagates.

The Rust SDK has no paying client, so nothing asks on your behalf: call `AppClient::authorize_spend` before you sign with `X402Flow`, then `consume_spend_authorization` with the signed payment's `req_id` or `release_spend_authorization` after a 402, following the same rules. Its README walks through them.

**This is a cooperative check, not hard enforcement.** 4mica's dashboard is not in the payment path: payments are signed locally, so anyone holding the wallet key can sign without asking, or leave `governance` out. Such a payment is still detected afterwards when the seller reports it: it raises an unauthorized-spend alert and counts toward your limits. Without `governance`, `client.fetch` behaves exactly as before.

`client.paymentFor(response)` returns what was paid for a response: `protocol`, `network`, `asset`, `amount` (a decimal string), `amountRaw` and `payTo`. It returns `undefined` when the request needed no payment, or when the seller failed the request without taking one.

## What your policy should handle

Spend limits are coarse. Your policy handles judgment: whether the seller, route, amount, network, asset, and task context are allowed before the agent makes the request.

| Policy area | Decision |
| --- | --- |
| Spend limits | Maximum price per request and maximum spend per task. |
| Seller access | Allowed sellers, domains, networks, and assets. |
| Approval | Thresholds that require a person or higher-level policy. |
| Blocking | Categories, routes, or sellers the agent should never pay. |
| Audit | Reason codes, logging, and alerting for every paid request. |

## Using `@x402/fetch`

If your client is already built on `@x402/fetch`, register the 4Mica scheme with it instead of switching to `client.fetch`.

```ts
import { wrapFetchWithPaymentFromConfig } from "@x402/fetch";
import { FourMicaEvmScheme } from "@4mica/x402/client";
import { privateKeyToAccount } from "viem/accounts";

const account = privateKeyToAccount(process.env.PRIVATE_KEY as `0x${string}`);
const scheme = await FourMicaEvmScheme.create(account);

const fetchWithPayment = wrapFetchWithPaymentFromConfig(fetch, {
  schemes: [{ network: "eip155:84532", client: scheme }],
});

const response = await fetchWithPayment("https://api.example.com/research");
```

<Note>
`@x402/fetch` only pays in assets its scheme client recognises. `FourMicaEvmScheme` recognises whatever 4Mica core lists for the network, so the seller's advertised USDC passes the client's spend controls and the default `$1` per-payment cap applies. Pass `spendControls` to raise the cap or allow other assets.
</Note>

## Signing rules

Before signing, validate the payment against your policy. The amount should fit the budget, the seller address should match the expected service, the route should match the task, and the network and asset should be approved.

If the payment crosses an approval threshold, collect approval before signing. If the task budget has no room left, return a controlled error so the agent can pick another service, ask for approval, or stop.

When a seller requirement does not clearly match policy, pause signing and [ask for help](mailto:support@4mica.io).

## Logging rules

Automatic payment should still be explainable. Each paid request should connect task ID, request ID, guarantee ID, seller domain, seller `payTo` address, route, amount, network, asset, policy version, reason for payment, and final result or error.

These logs answer "why did the agent pay?" after the task is done.
