4Mica v2 is live on Base mainnet. It changes three things about how agents pay
for an API.

- **Pay for what was used, not what was quoted.** The agent authorizes a
  spending cap, the provider starts work knowing the payment is secured, and
  the final charge is whatever the job actually costs.
- **The chain is out of the request path.** A payment is checked against the
  agent's reserved collateral rather than confirmed by a block, so it clears in
  milliseconds, no matter how busy the chain is. The chain only ever sees net
  positions, once per cycle.
- **One deposit, every provider.** There is no balance or channel to fund for
  each provider. The agent deposits once, pays any provider that accepts
  payment via 4Mica, and all of its obligations net down to a single payment.

Most of what an agent buys has a variable cost: a model call depends on the
tokens it generates, a scrape on the pages it processes, and an agent run on
the tools it ends up using. The provider needs to know it will be paid before
it does the work, when it does not yet know the price. Every payment system we
have inherited assumes the price is known before money moves. 4Mica v2 closes
that gap.

## How 4Mica extends agentic payments

4Mica v2 ships as an x402 scheme called `4mica-credit`. A provider advertises
it in the same 402 response as any other scheme, and an agent pays it with the
same fetch wrapper it already uses. We built it as a scheme, not as something
alongside x402, because a clearing layer is only useful if it is neutral to the
rails that run through it. We intend to carry MPP the same way.

What `4mica-credit` adds is a way to handle the case the existing schemes were
not designed for: a job whose price is unknown until it is done.

Let's illustrate this with one agentic workflow: An agent asks a scraping API
to crawl a site. It is willing to spend up to $1.00, and the crawl ends up
costing $0.37.

With `exact`, the provider quotes a price before the work. This may be the
right scheme for a fixed-price call, but for this job it means either guessing
$1.00 and overcharging, or not selling the job at all. With `upto`, the agent
authorizes up to $1.00 and the provider charges the actual $0.37 afterwards. It
seems to handle pricing, but what it leaves open is the reservation: nothing
sets the agent's funds aside while the crawl runs, so the same balance can back
other authorizations at the same time, and the provider only finds out whether
it is paid when it settles.

Both `exact` and `upto` require an on-chain transaction for every payment. For
a person buying one thing that is the natural design: the payment waits for a
block, someone pays gas on it, and the chain's throughput sets the ceiling. An
agent run that makes hundreds of paid calls reaches that ceiling quickly, and a
busy chain or a gas spike raises the cost of every call in the run. The x402
`batch-settlement` scheme fixes this issue with an idle escrow, but the escrow
is a channel between one payer and one provider, so an agent that uses 50
providers has to pre-fund 50 of them.

`4mica-credit` handles all three with one open collateral position. The agent's
funds are reserved at authorization, so the provider knows the $1.00 is there
before it starts. The solvency check is against that reserved collateral rather
than against a block, so no payment waits on the chain. And because one
collateral position backs every provider, the obligations across all of them
net into one on-chain movement per cycle instead of one per request.

So the question for 4Mica v2 was: how can a provider start work safely when the
final charge is unknown, without the agent locking money up with every provider
it uses, and without every payment waiting on a chain?

## How 4Mica secures a payment

Here is the same crawl on 4Mica:

1. **Authorize.** The agent authorizes a $1.00 cap. 4Mica reserves $1.00 of
   the agent's collateral and issues a signed receipt, which the agent sends
   with the request.
2. **Work.** The provider verifies the receipt on its own, without trusting
   the agent or calling a chain, and runs the crawl. It never waits for a
   transaction to confirm.
3. **Reconcile.** The crawl costs $0.37. The provider authorizes the unused
   $0.63 back to the agent.
4. **Settle.** At the end of the cycle, the $0.37 is tallied with everything
   else the agent owes and is owed, and only the net amount is settled
   on-chain.

The payment itself is a guarantee, a promise to pay, much like a card tap where
the merchant is paid later but is sure of it now. The receipt is 4Mica's signed
statement that the agent's collateral backs the payment. A signature from the
agent alone would prove nothing about whether the money is there. If the agent
never pays, the reserved collateral does.

## Why net settlement changes settlement economics

Every payment guarantee in a cycle, between any agent and any provider, nets
into one position per participant. In one cycle, 40 outgoing guarantees and 27
incoming ones become one net position, so one on-chain settlement replaces 67.
An agent that made a million requests across hundreds of APIs settles one
position for the cycle, and so does each API.

This is what an open collateral position enables. The agent never has to fund
an idle balance or a payment channel per provider; it deposits once, pays any
provider accepting 4Mica, and its obligations to all of them reduce to one
settlement. Every guarantee behind that settlement stays on record, signed by
4Mica, so the net figure can always be broken back down into the charges that
produced it.

In our current mainnet configuration, a cycle runs for 24 hours. After it
closes, 4Mica waits for any guarantees still open to resolve, then commits each
participant's net position on-chain. Net debtors pay within a payment window,
net creditors claim, and any debtor that does not pay is covered from its
reserved collateral.

For an agent, the whole lifecycle is gasless. Deposits, withdrawals, and the
cycle's net payment can all be submitted by a facilitator that pays the gas, so
an agent needs only stablecoins, not the chain's native token. What 4Mica
changes is the number of transactions a facilitator has to sponsor: one per
participant per cycle, instead of one per request.

## Start building

The snippets below target Base Sepolia (`eip155:84532`), which is where we
suggest you build first. Switching to Base mainnet is one field: set the
network to `eip155:8453`. Base mainnet needs `@4mica/x402` or `4mica-x402`
2.1.0 or later.

"No API keys" means no provider-specific key or billing account. The agent
still needs a wallet to sign with: one key, used at every provider.

On the agent's side, wrap the `fetch` you already have. It pays any endpoint
that advertises the `4mica-credit` scheme in its 402. Endpoints that only offer
`exact` still need a client for that scheme.

```typescript
import { FourMicaEvmScheme } from "@4mica/x402/client";
import { wrapFetchWithPaymentFromConfig } from "@x402/fetch";
import { privateKeyToAccount } from "viem/accounts";

const account = privateKeyToAccount(process.env.PRIVATE_KEY as `0x${string}`);
const scheme = await FourMicaEvmScheme.create(account);

const fetchWithPayment = wrapFetchWithPaymentFromConfig(fetch, {
  schemes: [{ network: "eip155:84532", client: scheme }],
});

const response = await fetchWithPayment("https://api.example.com/data");
```

On the provider's side, add one middleware and set a price per route:

```typescript
import { paymentMiddlewareFromConfig } from "@4mica/x402/server/express";

app.use(
  paymentMiddlewareFromConfig({
    "GET /data": {
      accepts: {
        scheme: "4mica-credit",
        price: "$0.01",
        network: "eip155:84532",
        payTo: "0xYourAddress",
      },
    },
  }),
);
```

This route charges a flat price, which is the simplest place to start. **To
charge for actual usage**, follow the
[metered billing demo](https://github.com/4mica-Network/4mica/tree/dev/apps/facilitator/packages/typescript/x402/demo).
It runs the cap-and-refund flow from the crawl example end to end, and the
[write-up](/blog/answering-x402-three-problems) walks through it.

- Paying for APIs from an agent: the
  [buyer quick start](https://docs.4mica.io/buyer/quick-start).
- Charging for an API: the
  [seller quick start](https://docs.4mica.io/seller/quick-start).
- Running an x402 facilitator and want to offer `4mica-credit` to your sellers:
  [get in touch](mailto:support@4mica.io).

## What's new for v1 users

If you integrated 4Mica v1, three things change:

- **Upgrade the packages:** `@4mica/x402` 2.1.0 or later and `@4mica/sdk` 2.x
  for TypeScript, `4mica-x402` 2.1.0 or later and `sdk-4mica` 2.x for Python.
- **Delete your tab configuration.** In v1, a buyer opened a tab with each
  seller before paying. v2 needs nothing opened first, so `openTab`,
  `extra.tabEndpoint`, `tabConfig` and `POST /tabs` are gone. A seller on
  `paymentMiddlewareFromConfig` and a buyer on
  `wrapFetchWithPaymentFromConfig` change nothing else.
- **Networks:** Base mainnet (`eip155:8453`) is production and Base Sepolia
  (`eip155:84532`) is for development. Ethereum Sepolia is retired.

The [changelog](https://docs.4mica.io/updates/changelogs) lists every renamed
call.
